  3. Commit the working milestone. Save the firmware, editable CAD, relevant settings, and trial notes together. Keep the simulation’s search-summary.json with the code revision that produced it. Record the actual parts and print-profile revision; reference any larger photos or videos from the experiment note.

  5. Export the notes. Use the notebook controls below, then save the exported JSON file with that milestone.

Use agents to accelerate the experiment

Your existing agentic workflow can handle implementation, plots, CAD scripting, and review. Give it the boundaries that matter in this new domain: units, actual hardware, timing, movement limits, and the observation that would support your hypothesis. For learning experiments, add the data contract and evaluation rules. Review those decisions yourself before accepting a plausible-looking result.

For a new robotics concept, use this with the relevant code and your exact parts:

I am an experienced software engineer learning physical robotics. Explain the mechanical, electrical, or control assumption behind this next experiment. Keep the existing hardware and limits. Help me state a prediction, an observable acceptance criterion, and the first diagnostic if it fails. Then implement the smallest change and list assumptions that still need measurement.

For a fault, describe what you saw before asking for a fix. “The board resets when the second servo starts” is more useful than “the servo code is broken.” Use this:

Be my debugging partner. Separate observed facts from assumptions. Use my exact part numbers, wiring, supply, code, and log below. Rank three plausible causes, then choose one low-risk measurement that distinguishes them. Tell me what result supports each cause. Preserve the known-working version and change one thing at a time.

Before you run generated motor code, request a review:

Review this change for units, pin assignments, supply assumptions, command timing, angle/rate bounds, startup behavior, and stale-command stopping. Name any claim that needs an exact datasheet or a physical measurement. Show the smallest useful check for each consequential issue; do not rewrite the whole project.

Review the diff against the experiment contract and predict the physical result before applying power. If the supply path is unclear, return to Chapter 02. A conversational coding assistant belongs beside the experiment; tested firmware or a deliberately deployed policy belongs in the live control loop.

For your first trained model, use an implementation brief that keeps the learning decisions visible:

Help me implement this frozen prediction task. Keep the episode split and untouched test set fixed. Add a simple baseline, fit preprocessing on training data only, train the specified small model, and compare on validation data. Report units, errors, and failure cases; do not select a model using test results or call the predictor a control policy. Ask me to explain what the model can and cannot establish before expanding the experiment.

Make restarting smaller than postponing

On a day when the full session is too much, do the two-minute version: open the working folder, read the last three-line note, and lay out the single part needed next. Labeling one connector or finding the correct USB cable can remove tomorrow's first obstacle.

Keep a “later” note for the tempting additions: a claw, depth camera, clever new gait, or a suspiciously spider-shaped chassis. Put the idea there and return to the current checkpoint. The idea is saved; it does not need to become today's dependency.

At the end of every session, write an action that starts with a verb and includes an object: “Run the same twelve-second gait three times” is ready to use. “Work on locomotion” asks your future self to plan the project again.

When the spider comes off the sketchbook page

Start with one leg held on a fixture. Given its joint angles, where does the foot land? That question is forward kinematics. Given a desired foot location, which angles could put it there? That is inverse kinematics. Measure the first answer before asking software to solve the second.

Then support a body off the ground while you check joint directions, cable clearance, and foot paths. Develop a slow scripted gait before adding learning. For a statically supported phase, keep the center of mass projected within the support region formed by the feet in contact; friction and contact still matter. A body that cannot carry itself through a repeatable baseline is not ready for a policy comparison.

Save that as a separate project with its own parts list and finish lines. Your next physical action remains the repeated trial in the table above.
