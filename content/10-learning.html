Run a fair parameter search, then follow a four-session plan for your first trained dynamics predictor.

You have already tried two commands: jump to the target, or ease toward it over 0.30 seconds. Both arrive. One moves faster; the other avoids the highest speed. That is enough to build a real optimization experiment. We will let the computer try 25 candidates and show its working.

The new skill here is experimental design: reset the robot, try a candidate, measure its behavior, select one, and test it on conditions that did not choose the winner. Your programming experience handles the implementation; the experiment must still earn its conclusion. This first runnable example searches a command parameter. After it, the first-model lesson plan takes you from data to fitted parameters and evaluation.

Session 10A · A tiny robot audition

Allow: 20–30 minutes. Bring: the working fieldbook-sim folder from Chapter 09. Finish: a chosen command ramp, a results table, and a comparison on two reserved link masses.

1. Decide what “better” means

For this exercise, better means a compromise between staying near the desired angle and avoiding high peak angular speed. We score every two-second trial using:

cost = RMS angle error + 0.03 seconds × peak angular speed

Lower cost wins. RMS means root mean square: square each error, average those squares, then take the square root. It gives one number for how far the joint is from its desired angle across the trial. Both terms in our cost have angle units; the 0.03-second weight expresses a preference we chose. It is not a material property, an energy measurement, or a universal safety limit.

The baseline jumps to the target immediately. Candidates take between 0.02 and 0.60 seconds to ramp up. Every candidate gets the same target, joint model, torque limit, starting position, and trial duration. Otherwise we could accidentally reward an easier test.

Save search_ramp.py beside joint_probe.py and joint.xml. Use the same terminal folder and environment as Chapter 09.

3. Inspect what the winning score hides

Look at the rms_error_rad and peak_speed_rad_s columns separately. The chosen ramp reduces peak speed by accepting more angle error during the movement. If I told you only that it was “better,” you would miss that tradeoff. A score is a compact statement of what you asked for; it is not a substitute for watching the behavior.

Now find the two Held-out lines in the terminal. The search used a 0.10 kg link. After selecting its winner, it tested both the winner and baseline at 0.08 kg and 0.12 kg. Those masses were reserved beforehand and did not pick the winner. In this edition's run, the chosen ramp also had lower cost in both reserved cases. That is evidence about these two variations, not evidence that it will control your real servo.

4. Change the preference, then predict the winner

In joint_probe.py, find SPEED_WEIGHT_S = 0.03. Change only that number to 0.00. Predict which type of command the search will prefer when peak speed no longer counts against it. Rerun search_ramp.py; it overwrites the previous results, so save a copy first if you want both. Then restore 0.03 and rerun once to leave the original experiment ready.

Check your prediction

The immediate step wins among the supplied candidates when the speed penalty is removed: it spends less time waiting for the commanded target to rise. This model's finite torque still limits acceleration. We changed the goal the search was solving, so a different winner is the expected outcome.

Read or copy the complete search_ramp.py
"""Search command rise times; evaluate the chosen setting on unseen link masses."""
import csv
import json
import random
from joint_probe import run_trial, save_trace

SEED = 7
TRAIN_MASS_KG = 0.10
HELD_OUT_MASSES_KG = (0.08, 0.12)  # decided before searching


def main():
    rng = random.Random(SEED)
    candidates = [0.0] + [rng.uniform(0.02, 0.60) for _ in range(24)]
    results = []
    for ramp in candidates:
        metrics, _ = run_trial(ramp, TRAIN_MASS_KG)
        results.append({"ramp_s": ramp, **metrics})
    best = min(results, key=lambda item: item["cost"])
    with open("search-results.csv", "w", newline="") as f:
        writer = csv.DictWriter(f, fieldnames=list(results[0]))
        writer.writeheader()
        writer.writerows(results)
    evaluations = []
    for mass in HELD_OUT_MASSES_KG:
        baseline, _ = run_trial(0.0, mass)
        chosen, _ = run_trial(best["ramp_s"], mass)
        evaluations.append({"mass_kg": mass, "baseline": baseline, "chosen": chosen})
        print(f"Held-out {mass:.2f}kg: baseline {baseline['cost']:.6f}; chosen {chosen['cost']:.6f}")
    _, rows = run_trial(best["ramp_s"], TRAIN_MASS_KG)
    save_trace("chosen", rows)
    with open("search-summary.json", "w") as f:
        json.dump({"seed": SEED, "train_mass_kg": TRAIN_MASS_KG,
                   "baseline": results[0], "chosen": best,
                   "held_out": evaluations}, f, indent=2)
    print(f"Baseline cost: {results[0]['cost']:.6f}")
    print(f"Chosen ramp: {best['ramp_s']:.6f}s; cost: {best['cost']:.6f}")
    print("Wrote search-results.csv, search-summary.json, chosen.csv, chosen.svg")


if __name__ == "__main__":
    main()

Your first trained model: predict one joint

You already use AI to help write software. Now you will build the smaller system underneath a learning experiment: a dataset, a parameterized function, an objective, and a test that can disagree with you. We will keep the same virtual joint so that learning the machinery does not also require inventing a new robot.

This is the next implementation plan. The supplied joint_probe.py and search_ramp.py run the earlier experiments; they do not collect the transition dataset below or train a neural network. You will implement those additions in a separate project folder, with an agent if useful. No training result or accuracy target is claimed here. Plan four 60–90 minute work sessions; stop at each artifact and resume from its next action.

Keep three jobs separate. The simulator advances a hand-specified physics model. Your learned dynamics model predicts what state comes next from examples. A controller or policy chooses what command to send. In this first project you train the predictor, then evaluate it offline. Its outputs never drive hardware.

Parameters are the numbers training fits, such as regression coefficients or network weights. A loss measures disagreement between predictions and examples; training adjusts parameters to reduce it. A gradient tells the optimizer how a small parameter change would change that loss. Inference is using the fitted parameters to make a prediction without updating them. A falling training loss is useful evidence that fitting works; it does not establish performance on new trials.

Session 10B · Freeze the question and collect transitions

60–90 minutes · Finish with a dataset and a split manifest

Read first: the statistical-learning overview in the free An Introduction to Statistical Learning with Applications in Python. Focus on inputs, responses, fitting, and generalization. Then write this contract before asking an agent to implement the collector.

ItemOur first experiment
QuestionGiven the current joint angle, angular velocity, and next held command, what changes over the next 20 ms?
Input[q_t, v_t, u_t]: angle in radians, velocity in radians/second, and commanded angle in radians, all available before the transition.
Target[q_next − q_t, v_next − v_t]. Predict both changes so the model can later advance its own state.
TimingRead the state, set one command, hold it through ten 0.002-second physics steps, then read the next state. One example spans 0.020 seconds.
MetadataEpisode ID, step, command-sequence seed, link mass, simulator/package versions, and model/configuration hash. Metadata organizes evaluation; it is not automatically an input feature.
  1. Reuse the supplied XML and simulator initialization in a new collector. Do not call the existing run_trial(): it validates positive targets and generates one ramp, while this collector needs a signed command sequence. Keep the XML’s axis, limits, damping, torque limit, and 0.002-second physics step. Create a fresh stationary simulation for every three-second episode. Change the command every 0.20 seconds, drawing it uniformly between −0.4 and +0.4 radians from a recorded seed. The collector records a transition every 20 ms while holding that interval’s command constant.
  2. Decide the split before fitting: 60 episodes at 0.10 kg for training, 20 for validation, and 20 for the final test. Give every episode a distinct command-sequence seed. Reserve another 20 episodes at each of 0.08 kg and 0.12 kg as separate mass-change stress tests. These are small teaching defaults, not a statistically certified sample size.
  3. Keep whole episodes in one split. Do not randomly mix neighboring time rows across splits or duplicate a deterministic command sequence across them. Training fits parameters; validation chooses settings and checkpoints; the final test estimates performance after those choices are fixed. See scikit-learn’s guidance on grouped and time-dependent evaluation.
  4. Plot one episode and audit three transitions by hand. Confirm the stated duration and units, then verify that inputs contain no next-state value, future error, or result-derived feature. Mark the first 80 ms after each scheduled command change as a motion window before examining model results.

Timing trap: the existing probe CSV stores position and velocity after each physics step, alongside the command that produced that step. Do not treat every same-row value as a pre-step input. The new collector’s explicit before/command/after record removes that ambiguity. An SG92R’s commanded angle is also not a measured physical angle; obtaining comparable real-world state would require sensing or estimation.

Pass when: every episode belongs to exactly one split, the plots agree with the log, and you can explain one input/target pair without the agent. Save the dataset, configuration, and split manifest. Next: build the baselines in Session 10C.

Session 10C · Give the model something honest to beat

60–90 minutes · Finish with a validation report for three baselines

Read first: the linear-regression section of the same book, then scikit-learn’s preprocessing and data-leakage examples. The important boundary is that fitting a scaler is also learning from data.

  1. Implement persistence: predict Δq = 0 and Δv = 0. Then constant velocity: predict Δq = v_t × 0.020 and Δv = 0. At a short horizon these can be strong baselines.
  2. Fit a linear regression from the three inputs to the two targets using training episodes only. If you scale inputs or targets, compute means and scales from training data and reuse those exact values everywhere else. Record how you handle any zero-variance column.
  3. Evaluate all three on validation episodes. Report angle-change RMSE in radians and velocity-change RMSE in radians/second separately. Show full-episode results, the predeclared motion-window results, and the worst episode. Long stretches near rest can otherwise make “predict nothing changes” look excellent.

Pass when: a saved report compares all three methods on identical examples, with physical units and no final-test use. Linear regression is already a trained model. If it loses, inspect timing, units, coverage, and plots before adding complexity. Next: keep that report fixed while you try a small network.

Session 10D · Train a small network you can account for

60–90 minutes · Finish with a checkpoint and learning curves

Read first: PyTorch’s Learn the Basics sections on tensors, datasets, building a model, autograd, and optimization. You can skim familiar Python syntax; trace where the examples compute loss, clear old gradients, backpropagate, and update weights. Their classification task differs from our two-output regression task.

  1. Use a separate CPU training environment and record the package versions you install. Keep the working simulator environment intact. Start with three input values, two hidden layers of 32 units with ReLU activations, and two output values. These are a deliberately small first architecture, not a claim that it is optimal.
  2. Reuse the frozen dataset and training-only scaling. Train on mean squared error of the standardized two targets so radians and radians/second are not mixed without a declared scale. Convert predictions back to physical units for every reported metric.
  3. Start with Adam at a learning rate of 0.001, batches of 256, and at most 100 epochs. An epoch is one pass over the training examples. Save the checkpoint with the lowest validation loss; stop after ten epochs without improvement. These are starting choices. If you change them, log the reason and use validation results, not the final test, to choose.
  4. First check that a tiny subset of training examples can be fitted closely. This is a debugging check for shapes, target alignment, and the update loop, not a generalization result. Then train on the full training split and plot training versus validation loss. Run the fixed recipe with three recorded initialization seeds; retain every result.

Let the agent write loaders, plots, and the training loop from your contract. You own the feature/target definition, split boundaries, loss, and interpretation. Ask it to walk through the shapes and units of one batch and to show which values change during one optimizer step. That review teaches more than accepting an impressive-looking loss curve.

Pass when: you can reload the weights and preprocessing state and reproduce predictions with training updates disabled. Follow PyTorch’s save/load example. Save code, package versions, seeds, split manifest, scalers, checkpoint, and curves. Next: freeze the recipe and open the test split.

Session 10E · Find out where the model stops being useful

60–90 minutes · Finish with a comparison and a stated limit

  1. Run the frozen baselines and network recipe on the untouched nominal-mass test episodes. Report per-output RMSE, motion-window error, and per-episode results; report all three training seeds rather than presenting only the best. A network that does not beat the simpler model is a valid result.
  2. Run the mass-change stress tests separately. This predictor has no mass input and learned at one mass; do not assume the same observed state and command identify all the changed physics. Label this as a change of conditions, not another sample from the training setup.
  3. On a test command sequence, start from its true initial state. Convert each predicted change into the next state: q_next = q + predicted Δq and v_next = v + predicted Δv. Feed that predicted state back into the model for one second. Use the recorded upcoming commands, but do not replace intermediate predictions with simulator truth. Plot angle and velocity against the simulator. Small one-step errors can accumulate into an unusable rollout.
  4. Write a short model report: task, data coverage, baselines, split policy, units, errors, failure cases, and what the model is not suitable for. If test results lead you to redesign the model, those results have become development feedback; reserve new final-test episodes for the next comparison.

Finish line: a fitted model, reproducible inference, and evidence of where it helps or fails. Predictive accuracy alone does not make it a controller or establish safe real-world behavior. Next: save the artifacts and choose one next experiment; use the physical-validation route below when you are ready to make a learned policy move a robot.

The same loop can audition a gait

For your crawler, a candidate can contain wave amplitude, frequency, phase offset, and turning bias. The score can use measured forward distance, unwanted heading change, and failed runs. Start with a small set of bounded candidates and the same reset and trial duration you used in Chapter 08. Do not send this joint experiment's numbers to the crawler: seconds of command rise and degrees of gait amplitude are different quantities.

A genetic algorithm adds a population, selection, and variation to this search pattern. Daniel Shiffman's Evolutionary Computing chapter and linked videos are a good next explanation. Watch for how a candidate is represented and how its fitness is measured. You already have those two pieces in the program you just ran.

Optimization by itself does not create feedback. A selected fixed wave remains open-loop: it will keep executing even if the floor changes. A controller that adjusts a wave from actual sensor measurements is a separate capability.

The next expedition: a crawler that reacts

Your long-term operator request can be “forward speed plus turn rate.” A policy chooses bounded gait adjustments from that request and observations. A neural network can represent that policy; reinforcement learning can fit it through rewards from interaction. This is a new job compared with predicting the joint’s next state. A genetic algorithm instead searches candidate parameters using selection and variation. Adversarial imitation can supply a motion-style objective when suitable reference motion exists; building a general-purpose GAN is not a prerequisite for locomotion.

Keep the execution boundary explicit: operator request + available observations → policy → local angle/rate limits and command timeout → actuators. Limits and the watchdog stay outside the learned model. A stalled laptop or invalid prediction must still reach the defined stopping behavior.

Keep this order for the next project:

  1. Measure one real joint. Record its response at the allowed loads and command rate. Ordinary SG92R commands are not measured joint angles.
  2. Build and check the whole crawler model. Match hinge axes, mass, actuator response, and passive-wheel contact. A chain of boxes on a generic floor is not the same mechanism. Replay one known gait and compare direction and displacement with the physical trials.
  3. Search the measured gait parameters. Reuse the baseline, reserved conditions, and results log you practiced here. Keep the physical angle/rate bounds.
  4. Add a measured heading signal and a simple corrective controller. Confirm that a turning request has a predictable effect before training a control policy.
  5. Wrap the validated experiment for learning. Use Gymnasium's reset/step interface, then try one PPO implementation. Evaluate against the simple controller on reserved conditions and several random seeds.

That is a new build, with its own finish lines. The supervised-model plan above teaches fitting and evaluation; it does not supply a crawler contact model or an RL trainer.

The simulator can use its exact position to score a trial. That does not make exact position available to the deployed policy. Do not put simulator-only truth into the policy's inputs unless comparable sensing exists on the robot. An IMU contributes rotation and acceleration information; it does not magically supply reliable floor displacement.
