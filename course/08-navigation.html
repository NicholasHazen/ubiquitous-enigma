08 · The first autonomous trip

Choose a destination.

Turn a point on your room map into a short, supervised journey—with evidence that the robot can stop and recognize when the trip has failed.

You already know how to drive the rover. This chapter changes who chooses the wheel commands: you choose a destination, and a navigation system selects the route and local motion. We will use Nav2, the ROS 2 navigation framework, while keeping the first trip short enough to understand from end to end.

Three jobs have to cooperate. Localization estimates where the rover is in your saved map. A planner proposes a route through available space. A controller turns the route into short-term velocity requests while current sensor observations influence which movements are acceptable. The motor controller still performs its local wheel-speed control; the navigation planner does not replace that loop.

We begin with a fixed map and AMCL, a lidar-based localizer. Stop SLAM before starting this setup so only AMCL owns map → odom. Local obstacle observations can change the space available for this trip without continually rewriting the underlying room map.

Integration status: this is a build-and-verification plan for your custom rover. The official packages supply navigation algorithms; your measured robot description, controller integration, command routing, and Nav2 configuration must be completed and checked. No physical waypoint run or stopping distance has been demonstrated by this book. Use the Jazzy first-robot setup guide alongside the bounded tasks below.

Session 08A · Make the robot contract explicit

One or more 45–60 minute blocks · Native Ubuntu host, saved map and measured rover · Result: a configuration you can review

Installing Nav2 does not connect it to a motor. Before enabling movement, write down the route from its final velocity output to the motor controller. There must be one selected command source at a time: manual control or navigation. A second teleoperation publisher left running can make a perfectly reasonable planner appear erratic.

  1. Open the robot description and compare its sensor offsets with the current physical mounts. Confirm live /scan, /odom, fixed sensor transforms, and odom → base_link.
  2. Repeat the manual stop and command-timeout tests from Chapter 04. Recheck at the intended battery state and load; additional sensors change both mass and wiring.
  3. Install the Jazzy navigation packages, then copy the configuration supplied with the installed nav2_bringup package into your project.
  4. Adapt that copy using the table below. Record the package versions and chosen controller plugin with the file.
  5. Have your coding agent review the file against the measured robot contract. You should be able to point to each parameter that controls geometry, speed, observations, and command type.
source /opt/ros/jazzy/setup.bash
sudo apt install ros-jazzy-navigation2 ros-jazzy-nav2-bringup
cp "$(ros2 pkg prefix --share nav2_bringup)/params/nav2_params.yaml" \

For footprint setup, work through Nav2’s footprint guide and visualize the resulting outline. A robot that fits at rest can still sweep a corner into an obstacle while turning. A horizontal lidar also cannot rule out an overhead obstruction or a drop-off. The first test zone therefore has known clearance and physically blocked stair access.

Session 08B · Convince yourself the robot knows where it is

45–60 minutes · Live sensors, motor outputs disabled initially · Result: a localized robot and sensible costmaps

Return to the live ROS domain used by the rover; the isolated replay domain from Chapter 07 is not the live system. Stop all bag playback and SLAM processes. Start the verified live acquisition and odometry stack, then start Nav2 with your reviewed files. This command assumes those files actually exist and the configuration gate above has passed.

ros2 launch nav2_bringup bringup_launch.py \
  map:=$HOME/home-rover/maps/room_001.yaml \
  params_file:=$HOME/home-rover/config/nav2.yaml \
  slam:=false use_localization:=true use_sim_time:=false

In RViz, display the saved map, laser scan, robot footprint, local costmap, and global costmap. Use 2D Pose Estimate to give AMCL an approximate starting position and heading that agree with the physical placement. The localizer refines that hypothesis from sensor observations; it does not know which room you placed the robot in merely because it loaded a map.

  1. With the rover stationary, inspect whether visible wall returns align with the saved walls. Check the robot heading against the room sketch.
  2. Verify that map → odom has one owner and that odometry continues to update. An apparently good single frame does not prove ongoing localization.
  3. Place a broad test obstacle in the scan plane and watch it appear in the local costmap. Remove it and observe whether later valid rays clear the space as configured.
  4. Inspect unknown areas and the inflated clearance around obstacles. Confirm that the first planned route will stay within surveyed, physically inspected space.

A costmap represents navigation preference and obstruction around the robot. Inflation raises the cost near obstacles so paths can leave clearance. Its margin must account for the measured body, localization uncertainty, and stopping behavior; shrinking it until a route appears is not evidence that the robot fits.

Check: the rover’s displayed placement agrees with its real placement, the footprint contains its physical outline, and the test obstacle appears and clears as expected. If walls do not align, diagnose initialization, map revision, frames, and scan timing before changing planner settings.

Session 08C · Go half a metre, then stop

45–60 minutes · Clear supervised floor area · Result: a recorded waypoint trial

Choose a destination about half a metre ahead in known free space. Mark it physically so the success claim does not depend entirely on the map display. Begin with the same low speed already demonstrated under manual control. Keep the operator stop within reach and the initial route clear of people and animals.

  1. Review the planned path in RViz before enabling the motor output. Check the entire swept footprint, not only the line through its centre.
  2. Enable the verified command route and submit the goal. Observe the robot, the reported navigation status, and whether its estimated position follows its physical movement.
  3. At the end, measure the physical final position relative to the mark. Record goal tolerance, final error, elapsed time, and any manual intervention. Use a provisional 0.15 m position target for these first short trips; the test establishes whether it is realistic.
  4. Repeat from the same marked start. Keep unsuccessful attempts in the log. A success message without plausible physical position and stopped wheels does not pass the trial.

Hold automatic recovery behaviors to the same visibility and clearance requirements. A default recovery can spin or reverse the robot. Configure the initial behavior tree and motion limits so it cannot perform an untested maneuver merely because the forward route failed. A cleanly reported aborted goal is useful evidence.

Check: save three trial records, including outcome, endpoint error, and interventions. Proceed when the short route behaves repeatably and stopping is dependable. If it oscillates near the goal, inspect minimum controllable speed, odometry, goal tolerances, and controller limits in that order.

Session 08D · Give the robot a reason to refuse

45–60 minutes · Same route and a broad test obstacle · Result: an honest navigation envelope

Your home changes. The first useful response to a change is often to stop or decline a route. Recognizing the obstacle as “laundry” can come later; geometric observations already provide a reason not to drive through it.

  1. Place the test obstacle on the planned route before starting. Choose a target tall enough to intersect the scan plane. Confirm that the costmap sees it, then request the trip. Accept a clearance-respecting alternate route or an explicit refusal.
  2. Cancel a short trip and verify that the rover stops. Record the observed delay and travel after cancellation.
  3. In a controlled low-speed test, interrupt fresh motion commands. Confirm that the local motor timeout stops the rover without depending on the Windows workstation or Spark responding.
  4. With motor output disabled first, interrupt the required sensor stream and verify the freshness guard inhibits motion. Re-enable only after the failure behavior is demonstrated. A velocity publisher that keeps repeating commands can hide a failed sensor.
  5. Restore the normal configuration and repeat the uncomplicated trip. Save both the failure test and recovery procedure.

Record the boundaries of what passed: floor surface, load, speed, sensor coverage, lighting where relevant, room/map revision, and failure handling. A scan-plane obstacle test does not establish detection of shoelaces, low toys, transparent surfaces, or stair edges. Those become separate experiments when you expand the operating area.

Chapter checkpoint: the rover can make a short supervised trip on the measured map, avoid or refuse a visible blocked route, and stop under the tested cancellation and timeout conditions. You have evidence for a bounded navigation capability rather than a claim of general household autonomy.
