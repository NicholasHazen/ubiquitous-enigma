05 · Sensors and evidence

Give the rover
eyes and a rangefinder.

Inspect each sensor now. The next chapter establishes its geometry, and Chapter 07 records a run you can replay.

The rover is manually controllable and passes its stopping checks. Now we add observations. The reference mapping route uses a horizontal 2D lidar and wheel encoders. Camera images supply our learning task; calibrated depth becomes useful when we reconstruct surfaces in three dimensions. These observations share a clock and a set of coordinate frames so we can later ask what was seen from a particular position.

A ROS topic is a named stream of messages. A driver translates a device’s interface into those messages. The names below are our course contract; the manufacturer’s driver may use different defaults. We will inspect the actual names and remap them deliberately. Copying a topic name into a command does not make a sensor publish it.

The onboard computer can be modest because the expensive experiments can run from recordings. It still needs to acquire messages and enforce the local command contract while the network is absent. We are choosing this arrangement to keep the first sensor and control connections on one native Linux machine.

WSL2 remains useful for Linux tools and offline work on Windows. Microsoft documents its networking modes, and USB access has a separate setup. For live robotics, check discovery, firewall rules, USB forwarding and timestamps explicitly. Keep the first live recording on the rover computer. The Spark hardware guide identifies its Arm architecture; it does not establish compatibility for every robotics package.

Session 05A · See one sensor before integrating three

45–60 minutes per device · Ubuntu computer, lidar, camera as available · Result: inspectable sensor messages

  1. Keep motor outputs disabled. Reuse the Jazzy installation verified at the Chapter 04 robot-computer setup gate. If you are starting with a bench sensor before finishing the chassis, complete that setup gate first, then return here. Record the sensor driver repository and commit or package versions.
  2. Install the selected lidar’s manufacturer driver. The reference candidate is the RPLIDAR A1 with Slamtec’s ROS 2 driver. Match the launch file and serial settings to the exact device. Inspect the scan in RViz; hold a flat object at a tape-measured distance and identify its returns.
  3. For a camera already on hand, first obtain a stable image using its own viewer and save stills for the model. The later RGB-D candidate is a RealSense D435i; verify its firmware, SDK, ROS wrapper and USB support together before committing to it. Use the manufacturer’s ROS wrapper as the integration reference. A colour image alone does not supply depth.
  4. Inspect the topic names and message types, then write a launch configuration that remaps the streams to the contract below. Leave optional depth absent until it actually works. Save device serial numbers so a second camera cannot silently become the first.
source /opt/ros/jazzy/setup.bash
ros2 topic list -t
ros2 topic info /scan --verbose
ros2 topic echo /scan --once
ros2 topic hz /scan

These inspection commands run after a driver publishes /scan. Stop the rate display with Ctrl+C. Its observed rate depends on the device and the machine; compare it with the configured sensor mode. A blank RViz view can come from a missing transform or unsuitable fixed frame even when messages exist.

See the first scan before the complete transform tree exists

  1. Keep the lidar stationary. In the single /scan message printed above, find header.frame_id and copy its exact value. This names the coordinates in which its ranges were measured.
  2. Run ros2 run rviz2 rviz2 in a terminal with Jazzy sourced. In Global Options → Fixed Frame, enter that actual laser-frame name. We deliberately use the sensor's own frame for this first inspection; no map frame is needed yet.
  3. Click Add → By topic, choose /scan with the LaserScan display, and confirm the display status. If it reports an incompatible QoS policy, compare the publisher details from ros2 topic info /scan --verbose with the display's reliability setting.
  4. Place the cardboard target in the scan plane, then move it a measured distance. Inspect the corresponding returns. A stationary sensor-frame view checks these readings; it does not establish a room map or robot localization.
  5. Save the RViz configuration as ~/home-rover/notes/lidar-bench.rviz and a screenshot with the frame and topic visible. Chapter 06 will connect this frame to the rover.

The official RViz guide explains displays and fixed frames. If messages arrive but the view remains blank, inspect the display's status before changing the driver.

Done: you can point to one real measurement, its units, timestamp and frame, and explain how it relates to the object you moved.

Chapter 06 teaches the frame geometry. You can bench-check each sensor now, but complete those frame and odometry checks in Chapter 06, then follow Chapter 07 to record the room. The order is connect → check geometry → record → map.

Move the learning experiment onto the rover

Your first model learned from hand-held images. A low camera sees different proportions, shadows and occlusion. Collect a new, named capture session from the mounted camera and label both target-present and target-absent images. Treat it as a stress test of the frozen model first. If it exposes a gap, create a new development dataset and reserve new final-test sessions. Do not quietly fold the old test images into training and keep reporting the old score.

The supplied learning program accepts ordinary image files. Exporting timestamped images from a bag and matching them to poses is a later integration task; Chapter 09 defines the evidence format. Keep an observation’s capture position distinct from the object’s position.
