Chapter 09 · Connect the two tracks

Give observations
a place and time

Your model has an opinion. Your map has coordinates. We will connect them without inventing facts between the two.

Suppose the robot's camera recognizes your chosen toy. The useful first answer is: “This image looked like the toy, from this viewpoint, at this time.” That is already more informative than a label floating over a video stream. It lets you inspect the source image, return to the observation area, and decide whether the evidence still matters.

A whole-image classifier cannot tell you which pixel contains the toy or how far away it is. In this chapter we store the robot's observation location and leave the object's location unknown. That distinction gives us an honest first spatial memory and a clear reason to add segmentation and depth later.

What runs now: the downloadable memory exercise uses Python's standard library and illustrative records. It runs on your Windows machine without ROS, a GPU, or a finished rover. Connecting live predictions to timestamped robot poses is a separate integration task described below. This memory never supplies collision decisions or motor commands.

Session 09A · Build a memory you can question

45–60 minutes · Python 3.10+ · Finish: explain exactly which observation supports an answer

Download memory.py, the illustrative observations, and the data contract into home-rover/memory/. Open PowerShell in home-rover, beside the Chapter 03 virtual environment. Reuse that interpreter; this exercise needs no additional packages. The image paths in the demo are placeholders; there are no corresponding household images or measured model results.

$LearnerPython = ".\.venv\Scripts\python.exe"
& $LearnerPython memory/memory.py import memory/demo.sqlite memory/observations-demo.jsonl
& $LearnerPython memory/memory.py recent memory/demo.sqlite --map-id room-a --map-revision v1 --target-id demo-toy --as-of 2026-10-27T19:20:00Z --max-age-minutes 60 --min-score 0.8

The importer should report three added observations. The query should return demo-01 as a historical candidate sighting and include the newer negative observation, demo-02, in its evidence list. The third row belongs to map revision v2, so it is excluded. A newer negative view does not prove the toy vanished: visibility, viewpoint, and classifier error can all change the answer.

  1. Inspect the candidate's timestamp, image reference, model identifier, and observer_pose. Confirm that object_position is null.
  2. Change the time window to ten minutes. At the stated replay time, both v1 rows are too old. An empty result means “no qualifying evidence,” not “no toy in the room.”
  3. Restore the sixty-minute window and change --min-score to 0.99. The candidate_sightings list becomes empty, while recent_observations still contains both v1 records. The score filter applies only to positive candidates; all recent evidence remains available for inspection.
  4. Query revision v2. Its coordinates belong to that map; comparing them directly with v1 would require a known transformation between the maps.
  5. Import the unchanged file again. Identical observations are retained once. Changing an existing record while keeping its ID produces an error; the original evidence remains intact.

Demo checkpoint: you can explain why an observation appears, why another is excluded, and why neither establishes a current object position. Keep the output beside the input file. This synthetic exercise prepares you for the real-record task below; it does not complete the robot’s spatial-memory milestone.

If the import fails: check that the input contains one complete JSON object per line and that timestamps include a timezone. Use the exact demo first. A map identifier, pose, and score are required because a label alone cannot support the spatial claim.

Keep evidence separate from interpretation

The observation template is a starting record for your own runs. Replace its example values; do not copy its zeros into a real recording. Store the image reference, capture timestamp, map revision, recording ID, model artifact identifier, target concept ID, label, score, and robot pose at capture time. The target concept ID separates classifiers for different things; it does not establish the identity of an individual physical object. A score of 0.9 is a model output, not an established 90% chance of correctness. Choose a display threshold using validation examples from Chapter 03.

Build the first records by hand before automating the join. The task below uses stationary, measured viewpoints so you can inspect each claim. A later timestamped adapter must preserve the original clocks and verify their relationship before joining streams. A pose from “when inference finished” can be wrong if the rover moved while the model was running.

For a binary model, record the score for the chosen label. If its output is p(target_present) and the decision is absent, the corresponding score is 1 − p. Keep the classification threshold with the run configuration. For example, learn.py predict might return {"label":"absent","score_present":0.12}. Its memory record uses "label":"target_absent" and "score":0.88. A present decision with score 0.92 becomes "target_present" with score 0.92. These numbers illustrate the conversion, not measured predictions. The memory query’s 0.8 filter is illustrative and applies only to candidate_sightings; recent_observations retains the matching evidence regardless of label or score. Neither output calibrates the classifier.

Many frames of the same object are correlated observations. Counting twenty adjacent positive frames as twenty independent confirmations overstates your evidence. Later object tracking will associate views with a persistent object hypothesis; it will still need to handle two similar toys, occlusion, movement, and conflicting observations. Preserve source records so a changed interpretation can be traced backward.

Session 09B · Give five real observations a place

One or more 45–60 minute blocks · Your saved model, mounted camera and checked map · Finish: import and inspect five real records

We now connect the parts you built. The synthetic database stays in memory/demo.sqlite. Your real records go in a separate file and database, so illustrative coordinates cannot quietly become household evidence. Use your current map revision and the same target object that trained the classifier.

  1. Mark two stationary rover poses in your bounded test area. Establish their x_m, y_m and yaw_rad in the current map frame using measured offsets from mapped reference surfaces and a checked heading. Record the measured endpoints and uncertainty in your notes. The pose refers to the base_link origin established in Chapter 06, not the camera lens. If you cannot yet express the marked poses in that frame, finish the frame/map checks before proceeding.
  2. Keep the camera fixed to the rover, inhibit motor outputs, and place the rover at each marked pose. Capture five distinct images across the two poses, including target-present and target-absent scenes. Put them in memory/images/. Record each image’s actual capture time with its timezone and its marked pose. Keep the rover stationary during each capture; do not substitute the time when inference finishes. A verified timestamped map → base_link pose from your recording is also suitable once that association works.
  3. Run the saved classifier on each image using the command below, replacing the filename with an actual image. Keep its output even when it is wrong. Use the label/score conversion above and retain the model artifact identifier, classification threshold, target ID and source run.
  4. Copy the observation template into five complete records. Give each a unique ID, actual image path, actual capture timestamp, current map ID/revision, measured observer pose, and object_position: null. Add a pose_source note such as marked_pose_manual_measurement and a pose_uncertainty_note describing the method. The importer preserves these provenance notes. Save one JSON object per line as UTF-8 memory/observations-own.jsonl.
  5. Import and query the file. Set the query’s map, revision and target to match your records, and use an --as-of time at or just after their latest capture, with a window covering all five. Open every referenced image yourself, compare the model decision with what you see, and check the pose against the marked viewpoint or recording.
& $LearnerPython learn.py predict runs/cnn-7 memory/images/marked-01.jpg
(Get-FileHash runs/cnn-7/weights.pt -Algorithm SHA256).Hash
& $LearnerPython memory/memory.py import memory/own.sqlite memory/observations-own.jsonl

The hash command identifies the actual neural weights for model_id; keep run.json with them so the preprocessing and source revision remain traceable. For the query, reuse the demonstrated recent command with memory/own.sqlite and your real identifiers and time. The program stores image references but does not verify that a file exists or that a pose is accurate; your five-record inspection supplies that check.

Real-record checkpoint: five observations from your own images and saved model are imported, and the query returns all five in recent_observations for the chosen map, target and time window. Every image opens, every pose has a documented physical or timestamped basis, and every object position remains unknown. If no positive candidate survives the display threshold, report that outcome and inspect the model errors; do not change its decisions to make the result look successful.

If the robot/map is not ready: save the completed demo and continue the next incomplete mapping task. You can prepare images and model outputs now, but leave unmeasured poses out of the real database. An automatic ROS image-to-pose adapter remains future implementation work.

Session 09C · Calculate a location only when you have the measurements

45–60 minutes · Paper, calculator, recorded poses · Finish: transform a measured point and name the missing inputs for an image

Imagine a separately measured point lies 1.0 m forward and 0.2 m left of the robot base. The robot is at map position (2.0, 1.0) m, turned 90° counterclockwise from map +x. Rotating the point sends forward along map +y and left along map −x. Its map position is therefore (1.8, 2.0) m.

x_map = x_robot + cos(yaw) * forward - sin(yaw) * left
y_map = y_robot + sin(yaw) * forward + cos(yaw) * left

Predict the answer at zero yaw: (3.0, 1.2) m. Draw both cases before using the formula. This planar example assumes the point already exists in the base frame. An image pixel needs calibrated camera intrinsics and valid depth before it becomes a 3D point; that point then needs the camera-to-base and base-to-map transforms at capture time. ROS camera optical axes differ from the body axes, as specified in REP 103.

When you add a detector or segmenter, an image region can define which depth samples belong to a candidate object. Inspect the depth distribution and foreground/background mixing before storing a location estimate. A bounding-box center can hit the wall behind a hollow or partly occluded object. Store the localization method and uncertainty with the estimate; retain the image and measured points that produced it.

Done: your sketch and arithmetic agree, and you can distinguish an observer pose, a measured object point, and an image-only prediction. The starter intentionally rejects object coordinates until a different localization schema is designed.

Let language select a grounded task

A future request such as “show me where you last saw the toy” can retrieve candidate evidence and display its image, age, and observation location. Embeddings would help match flexible language to descriptions. They do not supply missing geometry, guarantee identity, or refresh stale observations. Begin with the exact labels in the database; add semantic retrieval when a real query exposes that limitation.

For a first movement request, use a small catalogue of already tested viewpoints: “go to the doorway view” resolves to a known waypoint. The language component proposes a named action. A deterministic adapter checks the action, map revision, allowed area, current localization, and navigation readiness. It then submits a goal to Nav2's NavigateToPose action, monitors feedback, and reports completion or failure. Keep arbitrary scripts, motor values, and automatic pushing outside this interface.

This adapter is a later implementation exercise, not bundled functionality. First test a text-to-JSON version that cannot move anything: valid waypoint, unknown name, ambiguous reference, stale map, and cancelled request. Preserve the local stop behavior from Chapter 04. A conversation should explain the outcome of a navigation task; it should not become the motor controller.
