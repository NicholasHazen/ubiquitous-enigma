07 · The first survey

Measure one room.

Drive once, replay the observations, and check whether the map agrees with the room you actually measured.

We now have two imperfect accounts of movement. Wheel odometry says how the rover probably moved; the lidar says how nearby surfaces appeared from successive positions. Simultaneous localization and mapping, or SLAM, uses their agreement to estimate a route and a map together. When the robot recognizes a place it has revisited, a loop closure can correct accumulated drift.

Our first deliverable is a metric 2D occupancy map: a grid with a known scale whose cells represent occupied, observed-free, and unknown space. It is a slice through your room at the lidar’s height. It can describe useful layout and distances, but it cannot establish ceiling height, all furniture surfaces, or whether a low toy is beneath the scan plane.

We will use SLAM Toolbox for this first map. The depth-camera reconstruction you are interested in remains a later use of the same recording habit. Getting one measured floor map now gives us a place to attach those experiments.

Before this chapter: pass the frame and odometry checks. Your live acquisition stack must publish /scan, /odom, /tf, and /tf_static. The first session records those streams with no map → odom publisher running. The recipes below use actual stock ROS tools, but their success depends on the hardware bridge, calibration, and recording you build. They have not been executed on your rover.

Session 07A · Plan and record the room

One or two 45–60 minute blocks after the frame gate · One bounded test area · Result: a recording and its manifest

Choose a bounded area on one floor, with stair access physically blocked. Keep children and pets outside the first test area and clear small objects from the route. We are measuring a mostly static room before asking the system to handle your household’s normal motion.

  1. Sketch the room from above. Mark the start, two or three visible wall faces, and a short manual route with a gentle loop back toward the start.
  2. Measure three distinct spans between surfaces the lidar can actually observe. Include two directions. Record endpoints and measurement height so a baseboard measurement does not silently become a wall-face comparison.
  3. Declare a first acceptance target before viewing the map. Use absolute error no greater than 0.10 m on each reference span as a provisional layout goal. This is a course target to test, not a sensor specification or a promise of achieved accuracy.
  1. Complete Chapter 06’s frame and wheel checks. Set live nodes to use_sim_time:=false. Ensure the clock is sane before acquisition; record on the same computer first. Separate computers require clock synchronization and latency checks.
  2. Start only the validated drivers, wheel bridge and transform publishers. Stop SLAM, localization and navigation. We want raw wheel and sensor observations without previously computed map corrections.
  3. Record a stationary segment, then drive a short slow loop and return near the start. Keep the same bounded area and have the physical stop within reach. Do not record motion command topics for later replay.
  4. Stop recording with Ctrl+C. Save the computer/software versions, sensor identities, mount revision, wheel parameters, scene notes and measured reference distances beside the bag.
# On the robot computer, after all four topics pass inspection:
mkdir -p ~/home-rover/data
cd ~/home-rover
ros2 bag record -o data/room_001 /scan /odom /tf /tf_static

# After stopping the recorder:
ros2 bag info data/room_001

This is the minimum lidar mapping recording. When the colour streams work, add /rgb/image /rgb/camera_info to a new recording command and output directory. Add the depth pair only after its calibration gate. Check storage and message counts with a short recording before attempting a whole room. The output directory must not already contain a previous bag.

Use the run-manifest template. Never describe illustrative values as measured calibration. Keep the raw recording unchanged and put derived maps, exported images and models in separate directories.

If a recorded stream is missing: inspect the publisher’s actual name, offered QoS and rate with ros2 topic info --verbose. Confirm the recorder discovered it and retained static transforms. Fix one stream, then repeat a short recording. Do not proceed because the directory has a plausible file size.

Done: one recording contains the planned route, its raw topics and transforms, with the reference measurements and manifest saved beside it. This same data/room_001 bag is the input to the next session.

Session 07B · Replay the room without moving the robot

45–60 minutes · Ubuntu/Jazzy analysis environment · Result: one inspectable map

Recordings separate data collection from debugging. With motor power off and robot command processes stopped, you can compare mapping settings against the same observations. Use a separate ROS domain for the replay terminals, and keep live sensor and transform publishers out of that domain. These commands run in an Ubuntu shell; they are not PowerShell commands.

After following the official Jazzy installation, install the mapping tools. Create your project folders and copy the configuration supplied by your installed package:

source /opt/ros/jazzy/setup.bash
sudo apt install ros-jazzy-slam-toolbox ros-jazzy-nav2-map-server
mkdir -p ~/home-rover/config ~/home-rover/maps
cp "$(ros2 pkg prefix --share slam_toolbox)/config/mapper_params_online_async.yaml" \
  ~/home-rover/config/slam.yaml

Edit config/slam.yaml. Keep the installed solver settings initially. Set base_frame: base_link, odom_frame: odom, map_frame: map, scan_topic: /scan, and mode: mapping for our frame contract. Start with resolution: 0.05, a five-centimetre cell. Check the configured valid laser ranges against the actual driver and room; reject invalid measurements rather than inventing returns.

The upstream Jazzy example configuration uses base_footprint. Copying it unchanged would ask for a frame our current robot contract does not provide. This is the kind of small integration mismatch we want to catch before interpreting a poor map as a failure of SLAM.

In terminal A, start the mapper. Domain 71 is an example analysis domain; use it in every terminal participating in this replay, with no hardware-control nodes attached.

source /opt/ros/jazzy/setup.bash
export ROS_DOMAIN_ID=71
ros2 launch slam_toolbox online_async_launch.py \
  slam_params_file:=$HOME/home-rover/config/slam.yaml \
  use_sim_time:=true

In terminal B, source the same environment, set the same domain, and play the raw bag. Here ~/home-rover/data/room_001 is your actual bag directory, including its metadata; this is the directory recorded in Session 07A above.

source /opt/ros/jazzy/setup.bash
export ROS_DOMAIN_ID=71
ros2 bag info ~/home-rover/data/room_001
ros2 bag play ~/home-rover/data/room_001 --clock --rate 0.5 \
  --topics /scan /odom /tf /tf_static

Open RViz in the same domain with use_sim_time set to true, set its fixed frame to map, and display the map, scan, and robot frames. The --clock option supplies playback time; every consumer of the replay must use that time. For a later live mapping session, use use_sim_time:=false and the synchronized live timestamps instead.

Check: surfaces appear in a consistent place as the rover moves, and the route roughly agrees with your sketch. If nothing appears, inspect topic names, frame availability, and clock settings before tuning scan matching. If a wall doubles during turns, revisit odometry, sensor pose, timing, and wheel slip.

A replay trap: /tf contains many frame edges in one topic. Selecting that topic does not remove an old map → odom edge. If your bag was recorded while SLAM was running, collect a clean raw bag or explicitly filter the derived edge before recomputing SLAM. Do not let old and new mapping corrections compete.

Session 07C · Put numbers beside the picture

45–60 minutes · Map, reference sketch and measurement log · Result: an accuracy report

A map can look plausible while being stretched, duplicated, or consistently displaced. Measure the same three spans you recorded before the run. If you inspect raster pixels, use the map’s saved resolution; if you inspect points in RViz, use their map-frame coordinates. Record which wall boundaries you selected.

The example row demonstrates the calculation; it is not a result from this project. A 0.05 m grid resolution means cells are five centimetres wide. It does not establish five-centimetre accuracy. Range noise, pose errors, wall thickness in the raster, and how you chose the endpoints all influence the comparison.

  1. Compute the error for each span and compare its absolute value with the declared target.
  2. Inspect the route near the loop closure. A correction may improve alignment, but a false match can also fold the map. Check the room shape against your physical sketch.
  3. Collect a second independent survey and repeat the measurements. Agreement across runs is evidence of repeatability; agreement with tape measurements is evidence about accuracy.
  4. If a span fails, change one justified cause, then rerun the same recording before collecting another. Record which change helped and which problem remained.

Check: you can show the map, three measured comparisons, and the result of a second run. A failed target becomes a specific debugging question. It does not require starting a new robot or completing an entire SLAM textbook.

Session 07D · Save the map you can explain

30–60 minutes · Running mapper and project folder · Result: a versioned map package

While /map is available in the replay domain, save the occupancy grid for the next chapter. Use the same sourced environment, domain, and replay clock setting:

ros2 run nav2_map_server map_saver_cli \
  -f $HOME/home-rover/maps/room_001 \
  --ros-args -p use_sim_time:=true

Keep the resulting YAML and image together. The YAML supplies scale, origin, and occupancy interpretation. For live mapping, use use_sim_time:=false. A saved image without its metadata is a picture, not a complete navigation map.

Also serialize the SLAM Toolbox pose graph using its save/serialization interface if you want to resume that mapping session. A pose graph retains scan-and-pose relationships; the raster grid used by AMCL does not. Save the raw bag regardless, because it lets you rebuild results with changed software.

Put the bag identifier, software/package versions, copied configuration, reference measurements, room sketch, and a frame diagram beside the saved map. Give this collection a map_revision. Later observations will refer to that revision so a room-map correction does not silently change the meaning of an old location.

Chapter checkpoint: you have a saved metric room map with its metadata, a measurement report, and a raw run that can reproduce it. Your claim is now specific: “this map passed these checks in this room.”
